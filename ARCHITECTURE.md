# MTUAssistant architecture

See the [application overview](README.md) for features and local startup.

## Galaxy Map rendering

The home-page atlas is drawn directly from the M1105 sector/world database using PixiJS and pixi-viewport. Imported political borders and routes render above the grid using their stored colours. Downloaded PNG tiles are not required by the map. Refresh Sector Data downloads system data and TravellerMap metadata instead.

### Map detail

Detail switches according to CSS pixels per parsec (not device pixel ratio):

| Zoom | Detail |
| --- | --- |
| Below 10 | World circles and borders; no routes, world names or hex grid |
| 10–below 25 | World circles and hex grid; subsector capital (Cp) names only |
| 25–below 55 | World circles, hex grid, gas giants, bases and travel-zone rings; starport class; names for capitals and population 9+ |
| 55–below 95 | World circles, hex grid, gas giants, bases and travel-zone rings; full UWP and every world name |
| 95 and above | All details, including hex coordinates |

Map label fonts are 20% smaller at all zoom levels below 95 px/pc; full-detail fonts at 95+ are unchanged. Sector and subsector boundaries draw at every zoom. Label eligibility follows fixed bands in `wwwroot/js/MapGeometry.js`; no collision rejection, text budget, or zoom history suppresses eligible labels. Only off-screen text is culled. Subsector capital names are red; population 9+ names are uppercase (high-population eligibility uses 9+). Sector names remain visible, with subsector region names from 25 px/pc.

At close zoom, UWP sits at the top of the hex, below coordinates when shown; names have a four-pixel bottom margin. World circles grow with zoom. Zone rings have a minimum 2 CSS pixel stroke at every zoom level where they are displayed. Amber/red zone rings are fully opaque and do not affect symbol positions. Naval and scout symbols sit at upper/lower left; the gas giant is inset at upper right, aligned with the naval symbol. Click a marker or hex to select it; drag to pan. The viewport and selected world are remembered between visits in browser storage. The selection stores the sector ID and hex, and the world details are resolved from the current catalogue. Restoring a selection leaves the saved viewport in place. Each search dropdown item has two lines: the name in the primary style, then a muted line with the subsector on the left and the sector on the right, plus the sector hex for systems (e.g. "Regina" over "Regina … Spinward Marches 1910"). Subsector results show "Subsector C" on the left; a system in an unnamed subsector falls back to its subsector letter; sector results show "Sector". The lines come from `SearchResult.Title`, `Subtitle` and `Location`, and the dropdown may grow wider than a narrow search box, anchored to its right edge. Arrow keys move the highlight (wrapping at either end) and scroll the list just enough to keep it visible (`scrollActiveIntoView` in `SearchInput.js`, covered by `SearchInput.test.mjs`). Choosing a result fills the search box with its name only, selected so the next search can overwrite it. Selecting a system in the search dropdown (mouse or Enter) opens the map, pans smoothly to and highlights its hex at the current zoom (650 ms, with reduced-motion support), and loads the same details panel as a map click. Selecting a sector or subsector pans to its centre with the same animation, clears the world highlight and details, and preserves zoom. Search links use a stable target ID and a request token so selecting the same world again recentres it. Requests made while the map is loading are applied when it is ready; systems outside M1105 show an availability message.

The selected hex gets an animated selection marker (`wwwroot/js/HexSelection.js`), the hex-shaped counterpart of the Battlemap selection rings. It keeps the map's selection teal (`0x83e3d1`) and the faint 10% hex fill. Two concentric hex outlines carry dashes that march around the perimeter, bending through the corners: the outer hex sits on the hex edge with six corner-centred dashes (73/90 of each sixth, the Segmented arcs proportion, 3 CSS px), and the inner hex (78% size, 2 CSS px) repeats a long dash, gap, short dash, gap pattern every sixth. The outer dashes march clockwise and the inner ones counter-clockwise, at the Battlemap ring speeds (`RING_SPEEDS`, +20°/s and −35°/s as a fraction of a full lap), driven by ticker elapsed time. Only the marker is redrawn every frame; the rest of the map still redraws on view changes. At low zoom the marker keeps a minimum outer radius of 12 CSS px so the selection stays visible at Overview and Sector detail. With `prefers-reduced-motion: reduce` it stays still. The player presentation shows the same marker through the read-only map, using the selection already in the snapshot; no snapshot fields were added. It replaces the earlier static hex outline. Checks: `HexSelection.test.mjs` covers corner order against the map grid, perimeter points and wrapping, dashes bending through corners, dash lengths and gaps, inner/outer spacing, march speed and direction, reduced motion, minimum screen size, stroke widths and drawing.

**Jump measurement.** Right-click and drag on the Galaxy Map to measure a jump. A small white circle marks the centre of the hex where the drag started, a 2-pixel white line runs to the centre of the hex under the pointer, snapping hex to hex, and a label halfway along shows the jump distance in whole parsecs ("1 parsec", "6 parsecs"). This is the Battlemap measurement style, drawn in screen space. Distance is the hex-grid distance (`hexDistance` in `MapGeometry.js`), so it is correct across sector and subsector seams. Dragging off the atlas stops at its edge. Right-drag no longer pans; panning uses the left or middle button. The browser context menu is suppressed on the GM map. Releasing the right button makes the hex under the pointer the **jump destination**, which gets its own animated marker: the hex counterpart of the Battlemap's orange HUD bezel (`0xffa500`), with 24 radial ticks (a major tick on each corner) marching clockwise and six edge-centred inner dashes marching anticlockwise, at the same speeds, minimum size and reduced-motion handling as the selection marker. A right-click without dragging on the current destination clears it, and so does selecting the destination hex by clicking it or choosing it from search (restoring the saved selection when the map opens does not clear it); a cancelled drag or a hex outside any charted sector leaves the destination unchanged. The destination is independent of the selected world. It is saved in browser storage under `mtu.map.destination` as sector ID and hex, like the selected world, restored when the map opens, and re-resolved after a catalogue reload. The player presentation shows the destination marker and the live measurement from two optional snapshot fields, `destination` (hex centre and key) and `measure` (start and end hex centres). The Galaxy Map has no GM-only data. Older cached snapshots without these fields stay valid, and the presentation never measures or reads the GM's storage. Checks: `MapGeometry.test.mjs` covers jump distance against a breadth-first walk across sector seams, parsec labels, the measurement style and label position, snapping, clamping, destination choice, clearing by right-click, map click and search, cancelling, persistence, restore, reload and presentation mirroring. `HexSelection.test.mjs` covers the destination marker's ticks, dashes, motion, reduced motion, sizing and drawing, and `PresentationSync.test.mjs` covers validation of the new snapshot fields.

The System Data panel's **Stellar Data** section (formerly System Data) lists the system's stars, then three count badges in place of the old world-count sentence. Counts follow T5 Book 3: W is the total number of worlds, including the main world, asteroid belts (PBG B) and gas giants (PBG G), but not worldlets or satellites other than a satellite main world. **Gas giants** shows G in green when there is at least one, and an amber `0` when there are none, since the system then has no gas giant to skim fuel from. **Asteroid belts** shows B. **Other worlds** shows W − G − B − 1. The main world counts once towards W whether it is a belt, a satellite or neither, so the formula is the same in every case. A main-world asteroid belt (size `0` in the UWP, or the `As` remark) is not part of B, and the note below the badges says so; a satellite main world (`Sa`) also gets a note. An unknown count, or a W too small for its belts, gas giants and main world, shows a grey `?`. This replaces the earlier reading, which treated W as excluding the main world. Checks: the system-data checks in `MTU.RuntimeChecks/Program.cs` cover the T5 counts, belt and satellite main worlds, the `As` remark, known zeros, extended-hex PBG digits, W too small, and unknown counts.

`GET /api/map/overview` supplies sector metadata, world positions and compact world name/UWP/remarks data so zoomed-out capital labels are available immediately. The browser fetches detailed map attributes from `GET /api/map/sectors/{id}` for nearby sectors, with bounded concurrent requests and a client-side sector cache; these endpoints read cached server projections, not the database. Map descriptions and data projections live in MTU.Core; rendering geometry and detail thresholds live in `MTUAssistant/wwwroot/js/MapGeometry.js`.

## Shared system catalogue

After database migration, application startup awaits the singleton `SystemDataProvider.InitializeAsync()` before accepting requests. It loads sectors, subsectors, allegiances and systems once, using a short-lived database scope, and publishes a complete immutable `SystemCatalogue`. Concurrent initialization callers share the same task; a failed load prevents startup rather than exposing partial data. After a refresh, the provider reloads and atomically publishes a complete replacement snapshot; a failed reload leaves the prior snapshot available.

`SearchService`, `MapDataService` and `WorldSelectionService` share that catalogue across requests and Blazor circuits. Search retains its existing all-milieu scope, result grouping/limits and subsector context. Map and selection retain the M1105 filter. Map overview and per-sector DTOs are rebuilt when the catalogue changes, preserving existing API response shapes. Search returns fresh UI result objects so edits cannot affect shared data.

`CatalogueSystem` owns a stable system ID, location, `MainWorldData` and an immutable `Bodies` collection. Main-world data retains all currently stored system attributes. Bodies are currently empty; future `SystemBodyData` record types can supply stars, planets, moons and orbital information for an orrery without changing search or map contracts. No bodies or orbital positions are inferred from summary counts. Add future body-table loading to the provider's startup load and publish it as part of the same snapshot.

The runtime checks initialize concurrently, verify one read per source table, then close the test database and exercise search, map and selection. They also cover empty catalogues, milieu filtering, cancellation, protection from mutable search results, and the dropdown's title, subtitle and location lines for sector, subsector and system results.

## Refreshing sector data

Refresh Sector Data updates every sector in the configured M1105 area. For each sector it retrieves system data and TravellerMap metadata before replacing the sector's names, subsectors, allegiances, systems, borders and routes in a single database transaction. Existing sector IDs are retained. No sector or subsector image tiles are downloaded. A failed download leaves that sector's previous data intact and is counted in the progress dialog; cancellation retains already committed sectors.

Border paths and route endpoints (including cross-sector offsets) are preserved. Explicit colours take precedence over matching TravellerMap stylesheet rules; the original stylesheet and metadata fields are retained for future rendering. After a completed, cancelled, or interrupted refresh, the shared catalogue reloads any committed sector updates; open maps reload their data and restore the selection if the selected world still exists.

## Trading

Select a world on the map, then open Trading. Broker and Streetwise generate and save independent markets for each sector and hex. Common and matching goods use their listed lot sizes; extra D66 rolls add lots to existing entries. Broker rerolls illegal goods; Streetwise marks randomly rolled legal goods as stolen. Exotic goods have referee-determined tonnage. Each purchase price per ton uses a 3D roll, the saved skill DM, the strongest matching purchase DM and the strongest matching sale DM subtracted. The supplier DM is entered as a signed modifier and defaults to −2. Existing priced markets retain their original prices until rerolled. The resulting percentage and prices are saved with the market. Existing markets receive prices once on first opening without changing their goods or quantities. Markets survive system-row replacement during sector refresh.

Buying and Selling each have an independent active Traveller dropdown followed by mode controls. Each displays the selected Traveller total DM: Broker or Streetwise skill level plus the higher INT or EDU DM of the same Traveller. Missing skill uses the untrained -3 penalty reduced by the same Traveller's Jack-of-All-Trades level, to a minimum penalty of zero; skill zero is trained and receives no Jack-of-All-Trades bonus. This also applies to untrained Steward passenger modifiers. Jack-of-All-Trades does not grant Steward training or enable High passage. Unknown trading INT or EDU defaults to score 7 (DM 0), equivalent to UPP 777777 when the whole profile is unknown; the stored UPP is unchanged. Select a Traveller separately for each panel; Skill DM is blank and rolling is disabled until an active Traveller is selected. Buying and Selling Traveller and mode selections are remembered independently per campaign during the current user session, including navigation away from Trading. Inactive or deleted selections are cleared on reload. Modifiers refresh before each roll; saved markets retain the DM used when rolled. Current and destination worlds display UWP badges on the left and trade codes and travel zone badges on the right, matching Freight. Selling (Imports) can use the current world or an alphabetically sorted destination within six parsecs. Remote worlds load or generate their own saved selling market and show a red seven-day-old price badge. Selling lists goods with a positive matching Sale DM. Broker also includes common goods and excludes illegal goods; Streetwise excludes common goods and can include illegal goods. Roll calculates the sale price per ton from 3D plus the Selling section’s selected skill DM and strongest Sale DM, minus the strongest Purchase DM, plus the signed Buyer DM (default −2). Demand in tons is rolled using each commodity’s listed tonnage dice. Older saved Imports receive demand once without changing their prices. Sale results are saved independently by world and mode and marked outdated when reopened. They are sorted from highest to lowest price percentage.

The D66 goods, availability codes and lot sizes are based on [Trade Goods Dice Modifiers](https://github.com/timtoon/trade-goods) by Tim Heiderich (Mongoose Traveller 2nd edition, 2016); the aid identifies itself as CC BY-NC 4.0. Its ice-world availability codes have been normalized to TravellerMap's `Ic` code.

### Passengers and Cargo destination

Passengers and Freight are two tabs below the world selectors, with Passengers open first (see [Tabbed pages](#tabbed-pages)). The current and destination worlds apply to both tabs. The open tab's status badges sit at the right of the tab bar: the freshness badge, plus the mail traffic badge on Freight. Rolls, the entered Effects, the cargo capacity and any error on the other tab are kept while the page is open.

Passengers and Cargo uses the selected Galaxy Map world as the origin. The Destination world dropdown lists worlds within 6 parsecs, excluding the origin. When the page opens, it preselects the Galaxy Map jump destination, if it is one of those worlds. The jump destination is read from browser storage through `wwwroot/js/MapDestination.js`, the same module the map uses to save it, once the page is interactive. It is applied once, after any saved passenger and freight rolls for the origin have loaded, so it takes precedence over the destination those rolls were made for. Those rolls are kept and reappear when their destination is selected again. If the map destination is out of range, is the origin, or hasn't been set, the page keeps the saved-roll destination (or none), as before. The dropdown can still be changed by hand, and the page does not change the map destination. Trading does not use the jump destination. Checks: `MapDestination.test.mjs` covers the shared storage key, save, load, clear, validation and blocked storage; `TradeDestinations.Find` in `MTU.RuntimeChecks/Program.cs` covers matching by sector ID and hex and rejecting the origin and unknown worlds.

## Equipment

Equipment contains a shared database-backed catalogue of Armour and Weapons. Add and Edit use the same native modal dialog available from Traveller equipment; Delete uses the shared Delete Confirmation dialog. Armour and weapon notes appear in a muted Notes column. Range is numeric, nonnegative metres and accepts fractional values; tables display it as `<Range> m`. Damage, magazine, required skill and traits are text fields to allow rulebook notation; weights and credit costs accept decimals.

An armour's Required Skill is stored as one text value: the skill name followed by the level, such as `Vacc Suit 1`. Level 0 is assumed and left out, so `Gun Combat` means Gun Combat 0. The Add/Edit dialog edits it in two parts: a skill dropdown and a Level number (default 0, disabled while no skill is chosen). The dropdown starts with None, then lists a short set of skills that suit armour, each followed by its specialities from `CharacterSkillCatalogue`: Vacc Suit first, then Athletics, Flyer, Seafarer and Survival (for example `Athletics`, `Athletics (Dexterity)`, `Athletics (Endurance)`, `Athletics (Strength)`). The Core Rulebook only ties armour to Vacc Suit; the rest are a referee's choice, marked `RULES-ASSUMPTION` in `EquipmentSkillRules.ArmourSkills`, where the list can be changed. An existing armour whose skill isn't in the catalogue keeps it as an extra option, so editing never drops it. `EquipmentService.SaveAsync` normalises armour requirements on every save: `Vacc Suit 0` becomes `Vacc Suit`, and blank, `None` and `-` are stored as no requirement. Armour saved earlier keeps its text until it is next saved; both forms mean the same to `EquipmentSkillRules.MeetsArmourRequirement`. Weapons are unchanged and still pick from the fixed weapon skill list. There is no migration. Checks: `MTU.RuntimeChecks/SkillChecks.cs` covers splitting and joining the requirement, the level-0 rule, the dropdown list and its order, and what `SaveAsync` stores.

The catalogue page shows Armour and Weapons on separate tabs, with Armour open first (see [Tabbed pages](#tabbed-pages)). The search box, Clear and the Add button sit in the tab bar and act on the open tab. Each tab keeps its own search text while the page is open. Saving a new item opens the tab for its category, because the dialog lets a new item change category.

Open the Armour or Weapons tab of the [Traveller dialog](#traveller-dialog) to select catalogue items and add or remove them (Patrons and Enemies have the same tabs, and the Combat Tracker's Edit button opens the same dialogs). New Equipment opens the shared dialog and selects the newly saved item, ready for Add Equipment. Each catalogue item can be assigned once to each Traveller. The Traveller table shows comma-separated summaries: `Name (protection)` for armour and `Name (rangem, damage)` (compact metres in Traveller summaries) for weapons. Editing an assigned item updates the shared catalogue for all Travellers; removing it from a Traveller leaves the catalogue intact. Deleting a catalogue item confirms that it will also remove all assignments. Deleting a Traveller or campaign removes its assignments and preserves the catalogue.

The Equipment migration runs at application startup and retains existing campaigns, Travellers, skills and equipment-independent data. Runtime checks cover field persistence, summary formatting, assignment isolation, duplicate and invalid input handling, shared edits, removal, and cascading deletion.

### Traveller equipment options

Traveller equipment assignments store Quantity (minimum 1) and optional Scope, Targeting System, Laser Sight, Holographic Sight, FOF, PHUD and Smart Tracker flags. Existing assignments migrate to quantity 1 with no attachments. These settings are independent for each Traveller and do not modify the shared catalogue.

**Add Armour / Add Weapon dialog.** Below each equipment table, `+ Add Armour` or `+ Add Weapon` opens `CharacterEquipmentDialog` with nothing chosen. Its item list holds only catalogue items of that kind which the character doesn't carry yet, each shown with TL and either DR or range and damage. Armour shows the item and Quantity. A weapon also shows its Traits and, when it is ranged, the attachment checkboxes (a melee weapon shows a short note instead). Choosing another item keeps the quantity and any ticked attachments, and clears attachments the new item can't take. The Add button stays disabled until an item is chosen. The row's Options button reuses the same dialog with the item list disabled, so only quantity and attachments can change. `New Armour` / `New Weapon` still opens the catalogue editor; after a new catalogue item is saved, the Add dialog opens with it already chosen. Cancel or Escape leaves the saved assignment unchanged. The standalone equipment panel (no kind) shows both Add buttons.

Attachments are available only for weapons whose numeric Range is greater than zero; range zero is treated as melee. Smart Tracker implies Intelligent Weapon. Quantity appears in both Traveller equipment tables. Weapon attachment summaries appear in secondary text beneath catalogue Traits, using labels such as `Scope, Laser Sight, PHUD`. Weight and credit columns retain their catalogue values per item.

## Sector Data view

The Refresh Sector Data navigation item opens `/sector-data` without starting a refresh. The page reads database counts for sectors, sector names, subsectors, systems, allegiances, borders and routes, and lists loaded milieus. Refresh Sector Data Now runs the original refresh action and progress dialog. While a refresh is running the button can reopen its progress dialog. Statistics reload after completion, cancellation or failure so any committed partial updates are reflected.

A completed refresh stores its real UTC completion timestamp in the database. The Last Refresh badge displays that date in the browser's local time as yyyy-MM-dd, with the full local timestamp on hover. Cancelled or faulted refreshes retain the previous completed timestamp. A completed run may include individual sector failures, as reported by the existing progress dialog. Until a refresh is recorded, the badge displays Not recorded. Counts use an independent database scope and a read transaction to avoid sharing the refresh worker's DbContext.

### Population statistics

Sector Data includes total known main-world population for loaded charted space and the ten largest populations by major polity, followed by Others. Rows show exact whole-person totals and percentage shares. The first two letters of allegiance codes define the major polity, case-insensitively, across sectors within one milieu. All Im* allegiances aggregate as Third Imperium (Im). Other names use two-letter metadata when available, a common recorded family name, or the prefix as a fallback. Unknown allegiance is retained as Unspecified polity. If several milieus are loaded, a selector keeps their populations separate and defaults to M1105 when available.

Population follows Traveller Map Second Survey: PBG population multiplier times 10 raised to the UWP population exponent. A zero multiplier with a positive exponent uses the documented legacy multiplier of one. Unknown or invalid population data is excluded and reported as a system count; no population is inferred for other system bodies. Decimal arithmetic avoids aggregate 64-bit integer overflow. The top ten plus Others reconcile exactly with the displayed total, and refresh completion recalculates the figures from the database. Source: https://travellermap.com/doc/secondsurvey#population-exponent

## Patrons and Enemies

The campaign-specific `/patrons-enemies` view supports adding, editing and deleting characters with token image, name/occupation, race/gender, two quirks, UPP and skill level. Occupation, gender and Quirks 2 use secondary styling beneath their primary values. Generated UPP uses type, racial and skill-level adjustments and displays in uppercase. Skill level offers 12 numbered ratings: Recruit, Novice (default), Adept, Practitioner, Veteran, Expert, Master, Elite, Champion, Hero, Mythic and Legendary. The generation buttons create reviewable drafts. Before the first Save, changing occupation or skill level rerolls draft skills. Saved NPCs lock type, occupation, race and skill level so these fields cannot trigger regeneration.

Skills and Equip reuse the same inline editors and catalogue dialogs as Travellers, including token headers, named/specialised skills, armour-specific protection, quantities, attachments, and worn/equipped state. NPCs use explicitly classified character records with a one-to-one NPCs profile so these existing editors and relationship tables remain shared. Player Traveller listing, mail/passenger modifiers and party trading exclude NPCs; player character save/delete operations reject NPC IDs. Patron/enemy operations are restricted to the current campaign and cannot edit player characters. Deleting an NPC cascades its profile, skills and equipment assignments while preserving catalogue items. Existing characters migrate as player Travellers.

### Character schema naming

Shared records use Characters / CharacterEntity and CharacterService. NPCs / NpcEntity stores the one-to-one NPC profile, with NpcService providing NPC operations. CharacterSkills and CharacterEquipment use CharacterId foreign keys; the shared character name is Name. Shared editors and helpers use Character naming. The Travellers and Patrons and Enemies screen names remain unchanged. The CharacterNaming migration renames populated tables and columns in place, preserves IDs and relationships, and supports rollback without deleting character data.

### Random NPCs

Ally/Enemy rolls D66 on the original 36-type occupation table, 1D for race (1-3 Human, 4-5 Aslan, 6 Vargr), and 1D for gender (1-3 Male, 4-6 Female). Choose Skill Level beside the generation buttons before generating (default Novice). Recruit through Legendary represent levels 1-12 and receive two skill rolls per level (2-24 rolls). Each profession has eleven distinct catalogue skills indexed by unmodified 2D totals 2-12. Core skills sit near 6-8 (especially 7), with background skills toward 2 and 12. The first acquisition gives rank 0; each duplicate increases the rank by one, up to rank 5 (six acquisitions). Further rolls of a capped skill are rerolled until another skill is selected, without consuming the acquisition budget. The number of distinct skills can be smaller than the roll count. Pools use the existing catalogue and always specify a speciality for skills that have them, such as Electronics (Computers), Athletics (Dexterity) and Gun Combat (Slug). Different specialities of the same base skill can appear in a pool. Acquisitions and the rank-5 cap are tracked independently by full speciality name. When saving, each acquired speciality also records its base skill at rank 0; speciality entries are recorded only at rank 1 or higher. Multiple specialities share a single base entry. The draft preview shows this recorded form while retaining the full acquisition history until Save.

The draft previews generated skills. Changing skill level in a generated draft rerolls its skills, age and UPP. Names, UPP and quirks are generated and remain editable. Name remains editable before and after saving. Nothing is written until Save; Cancel discards the draft. New NPC profiles and generated skills save atomically. Saved profile edits leave generated properties unchanged; skills remain separately editable through the Skills panel. Age is rolled as 16 + 4 × level + 1D - 3 (maximum 67 at level 12), displayed in the list and editable in the draft. The NpcAge migration adds a nullable age column at startup; existing NPC ages remain unknown. Deterministic generation and database checks are included in MTU.RuntimeChecks/NpcGenerationChecks.cs.

### NPC types and filtering

NPCs persist a type selectable before the first Save: Ally/Enemy, Patron/Civilian or Combatant, displayed in the list. The NpcType migration adds the type column at startup and classifies pre-existing NPCs as Ally/Enemy. Ally/Enemy uses the original archetypes. Patron/Civilian uses all 36 occupations from the supplied Random Patrons D66 table, each with eleven specialised catalogue skills arranged around the 2D bell curve. Combatant uses a shared military grunt pool and starts with Occupation Unspecified; Gun Combat (Slug) sits at 7, with Leadership at 2 and Tactics (Military) at 3. All types use the selected skill level, existing race/gender/age rolls, rank-5 cap, independent specialities and base-skill recording rules. No draft is stored until Save. The Add Character button is removed: start with a generation button at the chosen skill level. In the editor, NPC Type appears before Occupation and determines its alphabetised profession choices. Changing type or occupation rerolls skills while preserving age; changing skill level rerolls skills, age and UPP. Combatant professions include Guard, Marine, Mercenary, Militia, Scout, Security Officer, Sniper and Soldier, sharing the grunt pool. Existing custom occupations are retained in the read-only saved profile. Cancel discards all rerolls; Save atomically replaces the previous skills when rerolled.

Filter NPCs searches Name, Occupation, Race, skill-level name/number, and skill names/ranks case-insensitively as text is entered. NPC type labels are searchable as well. Clear restores all campaign NPCs; no matches show a dedicated empty state.

### NPC UPP generation

Roll six lots of 2D for STR/DEX/END/INT/EDU/SOC. Ally/Enemy retains rolled order. Patron/Civilian randomly assigns the lower three within STR/DEX/END and the upper three within INT/EDU/SOC; Combatant reverses those groups. Aslan applies STR +2 and DEX -2; Vargr applies STR -2, DEX +1 and END -1. Levels 2, 4, 6 and 8 each add one to a random attribute; levels 9-12 each remove one from a random attribute. Attributes are clamped to 3-12 after racial modifiers and each level adjustment; an adjustment at a boundary remains at that limit. UPP is encoded as six uppercase hexadecimal digits (A/B/C for 10/11/12) and remains editable. In unsaved drafts, changing race, type or skill level regenerates UPP; changing profession preserves it. Existing saved NPCs are not automatically regenerated.

### NPC names and saved profiles

NPC generation selects a name from race- and gender-specific pools: Human given/family names, Aslan given/clan names, and Vargr given/pack names. These are original flavour names. In a new draft, selecting Human, Aslan or Vargr regenerates the profile. Changing gender refreshes the automatic name only while Name still matches the previous suggestion; a referee-entered name is preserved when gender changes. The Name field stays editable for saved NPCs. Saved NPC Type, Occupation, Race and Skill Level controls are read-only, and their regeneration handlers also reject saved profiles. Other editable fields and the Skills/Equip panels remain available.

### Race selection and manual profiles

Race is a dropdown containing Human, Aslan, Vargr, Droyne, Bwap, K'Kree, Hiver, Dolphin, Gorilla and Robot. Only Human, Aslan and Vargr support automatic generation. Selecting another race clears only Name, Gender, Age and UPP for manual entry. Occupation, generated skills, quirks, token, NPC Type and Skill Level are preserved. Changing type or profession can reroll skills, and changing skill level rerolls skills without populating manual age or UPP. Empty UPP is preserved on Save for manual races. Selecting Human, Aslan or Vargr again generates name, gender, age, UPP and skills for the current type and level. Saved NPC Race remains read-only.

### NPC quirks

Each newly generated NPC rolls D66 twice on the supplied 36-entry Character Quirks table. Matching results retain the first quirk and leave Quirks 2 blank; duplicates are not rerolled. The two quirk fields remain editable and persist with the NPC. Race, profession and skill-level changes retain existing quirks, as do edits of saved NPCs.

### Combatant loadouts and editor layout

New Combatants receive a proposed Supply Catalog loadout: usable armour, a ranged infantry weapon and a melee backup where available. Selection favours conventional cloth/flak/ballistic armour, respects explicit armour skill requirements, excludes battle dress, and prefers standard rifles/carbine/pistol patterns suited to the NPC's Gun Combat speciality. Heavy launchers/artillery and natural weapons are excluded from the standard loadout. Armour tech-level variants prefer the lower TL within the same preferred class. Choices are shown before Save, are refreshed when draft skills change, and are persisted atomically at quantity 1 with Worn/Equipped enabled. Catalogue entries are reused rather than copied. Missing categories are skipped; an empty/incompatible catalogue leaves no proposed loadout. Existing saved NPC equipment is never reset by profile editing and remains editable through Equip.

The editor uses three desktop rows: Name / NPC Type / Skill Level / Occupation / Race; Gender / UPP / Age; and Quirks 1 / Quirks 2 in equal halves. Narrow screens wrap the identity fields into two columns and stack fields on small phones. Skills, equipment preview and token controls follow below.

## Map presentation

On the Home map, the cast icon (**Present map**) opens a separate read-only map window. Move it to the presentation monitor and use the browser's fullscreen command (F11 on Windows). It follows the Admin map's centre, zoom, search navigation and selected hex. A different window size shows more or less surrounding space at the same map scale. Admin navigation and campaign controls are omitted. ## Scenes and Battlemap

The docked Combat Tracker stores the encounter roster for each scene, including combatants that have not been placed. Active Travellers appear automatically, once each, before NPCs; inactive Travellers are excluded and are reconciled when returning to the Battlemap. Inactive Travellers, NPCs and animals don't count. It sits next to the Open badge, and since Add Travellers moves the whole party it normally marks one scene. Covered in `SceneChecks.cs`.

The minus button unplaces a token while retaining its tracker entry; × removes an NPC instance from the encounter. Each placed token occupies one grid square and moves/resizes with the grid and zoom. Uploaded character images retain their aspect ratio; missing/unusable images show initials. Drag tokens to snap between squares and drag the background to pan. The Cast glyph opens a read-only Battlemap presentation paired to this Admin tab in the same browser profile/origin. It follows camera, token and grid updates. Navigating away retains the last presented view; returning resumes updates. Close clears the player map. Presentation snapshots use a separate BroadcastChannel and storage key from the Home sector map.

Scenes are campaign-specific battlemap definitions with a background image stored in the database (PNG, JPEG, GIF or WebP, maximum 4096 × 4096 pixels), name, grid size (default 100 image pixels), colour (black), opacity (50%) and line width (2 screen pixels). Scenes appears in navigation immediately above Battlemap. Battlemap is disabled until a scene is opened. Opening replaces the currently open scene and starts fit-to-page. The Battlemap shows the image with its configured square grid; drag to pan, use +/− or the mouse wheel to zoom, and Fit to page to reset. Zoom anchors to the mouse position when using the wheel. Right-click and drag on the Battlemap to **measure**. A small white circle marks the centre of the square where the drag started, and a 2-pixel white line runs to the centre of the square under the pointer (pointers off the map stop at the edge square). Measuring only starts on the map image and isn't available while placing a token. In combat, selected tokens get textured, counter-rotating selection rings (`wwwroot/js/SelectionRings.js`). Each target gets orange (`0xffa500`, `RING_TINTS.target`) **HUD bezel** rings. Both ring colours are fully opaque. The target line and its start dot use the same solid orange, while movement trails stay white at 25% opacity. Each HUD bezel has: 48 radial ticks, every fourth one major (major ticks 11 px wide, minor 7 px, widened from the original 7 and 4.5 px for visibility), plus four 74° inner arcs offset 45°. The outer ring spans `RING_DIAMETER_RATIO` (1.6) displayed token widths, using `tokenDisplaySize()` and the zoom, so it follows panning, zooming, moves and placement. Rotation uses ticker elapsed time: the outer ring turns +20°/s (clockwise) and the inner ring −35°/s. With `prefers-reduced-motion: reduce` the rings stay still. Rings show only in combat, never on a dead active combatant, and they disappear when combat ends, the target is cleared or the token is removed. Fog of war is switched on or off per scene with the cloud button after Undo fog. It is **off by default**: no fog is drawn in the GM view or the player presentation, every visible placed token is shown to players, and fog editing, the Fog brush and Undo fog are disabled. Turning it on shows the scene's saved fog in both views; turning it off hides fog but keeps the painted fog, so turning it on again restores it. The setting is saved with the scene (the SceneFogEnabled migration adds it, and existing scenes start with fog off) and is kept when the scene is edited. Switching fog clears the fog undo history. When fog is on, it is edited directly on the Battlemap with modifier-drag; there is no separate fog mode. **Shift+drag** clears fog, revealing squares to the players, and **Ctrl+drag** adds fog back. A plain drag still moves tokens or pans the map. The modifier is read when the drag starts, so pressing or releasing keys mid-stroke does not switch modes. Holding Shift and Ctrl together is ignored and behaves as a plain drag. Shift/Ctrl+drag starting on a token paints fog instead of moving the token, and Shift/Ctrl+double-click does not select it. While a token is being placed, modifiers are ignored and the click places the token. The cursor becomes a crosshair while Shift or Ctrl is held over the map. Fog brush (1, 3, 5 or 9 squares, default 3) sets the stroke width. Holding Shift or Ctrl and turning the mouse wheel steps the brush through the same sizes (wheel up is larger), stopping at 1 and 9, and updates the dropdown; without a modifier the wheel zooms as before. Each completed stroke saves immediately; a failed save rolls back, and Undo fog reverts up to 20 strokes. Strokes in progress are never sent to the presentation, and the player snapshot only includes tokens on revealed squares. In the player presentation the fog has a **soft edge** three squares wide that straddles the hard edge of the fog: it starts one square inside the revealed area, is a third dark at the hard edge and is solid black two squares into the fog. It darkens evenly with straight-line distance across the nearest hard edge, so corners are rounded. Revealed squares a full square or more from any fog are fully clear. The outermost revealed squares are slightly dimmed, along with any tokens standing on them, and a revealed area only one square wide is dimmed throughout. `fogGradientSquares` sets the total width, `fogGradientLead` how much of it lies inside the revealed area (0 starts the fade at the hard edge) and `fogGradientCurve` the shape (1 is even; below 1 darkens sooner). Players can therefore dimly see the map image under hidden squares within two squares of a revealed one. That is intended and applies to the image only: tokens, movement trails, movement ranges, measurements and the GM pointer are still cut off at the hard square boundary. The snapshot is unchanged; it carries the revealed squares and the presentation derives the gradient from them. The GM view keeps hard-edged squares at 55% so fog can be painted exactly. The gradient is one black sprite in the fog layer whose alpha comes from `fogGradientField` (`wwwroot/js/FogOfWar.js`), drawn into a small canvas texture at four texels per square (fewer above 256 squares across, keeping the texture near 1024 texels) with linear filtering, and cropped to the image so a partial last square draws nothing beyond the map. It is rebuilt only when the revealed squares or the grid size change, not on every pan or zoom snapshot. If the gradient cannot be drawn, the player view falls back to solid black squares rather than showing no fog. **Polygons (experimental).** The Polygon toolbar button switches the GM's Battlemap into **Polygon mode**, for drawing closed polygons on the map. In Polygon mode a left-click adds a point: the first click sets the origin, a preview line runs from the last point to the pointer, and a small white ring with a dark edge shows where the next click will land. Clicking the first point again completes the polygon once it has three points (it gets a larger white ring when a click there would close it), and the polygon is saved at once. Points snap to the nearest square corner or square centre that is on the image (`polygonSnap` in `wwwroot/js/Polygons.js`), never to the middle of a square's side. A left-drag still pans, since a press that moves less than 4 pixels counts as a click, and the wheel still zooms. While the mode is on, tokens can't be moved or selected, fog can't be painted, and right-drag doesn't measure or target; placing a token from the Combat Tracker still works. A right-click takes back the last point of the polygon being drawn, cancelling it when only the origin is left, and Esc cancels it outright. When nothing is being drawn, a right-click inside a finished polygon, or within 6 screen pixels of its outline, deletes it; where polygons overlap the most recently drawn one goes first. **Undo polygon**, shown while the mode is on, takes back a point while drawing and otherwise reverses the last add, delete or open/close, up to 20 steps. Like Undo fog it has no redo, and its history is lost when the page is reopened. Leaving the mode discards an unfinished polygon. The mode itself is not saved. Each polygon is **active** or **inactive**. An active polygon is solid and blocks line of sight; an inactive one is ignored, like an open door. New polygons are active. **Outside Polygon mode, a left-click on a polygon switches it between the two** and saves the change; a click is a press that moves less than 4 pixels, a press on a token still moves the token, and the cursor becomes a pointer over a polygon. Polygons are drawn in screen space above the fog, with 2-pixel lines that stay the same width at every zoom (`polygonStyle`). In Polygon mode they are red (`polygonColour`): an active polygon has a solid outline and a very light red fill (10%), an inactive one a fainter outline (45%) and no fill. Outside Polygon mode they are blue (`polygonIdleColour`) and faint, so they stay out of the way of play: a 30% outline, with a 15% fill when active and no fill when inactive. Polygons are **GM-only**: they are never added to the player snapshot, and a read-only presentation map never holds, draws or toggles any. They are stored with the scene as JSON in `Scenes.PolygonState` (the ScenePolygons migration adds the nullable column, and existing scenes start with none) as lists of points counted in half squares from the map's top-left corner, so a corner has two even values and a centre two odd ones, plus the `Active` flag; polygons stored without the flag are active. `SceneService.SavePolygonsAsync` replaces the scene's whole set. It rejects polygons with fewer than 3 or more than 200 points, more than 200 polygons, points off the image or not on a corner or centre, the same point at both ends of a side, scenes in another campaign, and saves made against an older image or grid size. A rejected or failed save puts the map back as it was. Because points are positioned by the grid, changing the grid size or replacing the background image discards the scene's polygons, as it does fog; changing only the grid's colour, width or opacity, or renaming the scene, keeps them. Rolling the migration back drops the column and the polygons with it. **Line-of-sight fog (experimental).** With fog of war on, the fog is cleared from every square the **selected Traveller** can see. Two distances, both in whole metres from 0 to 1000 and both 0 by default, set how far that is. The **Ambient Light** belongs to the scene: it is the Ambient light (m) field on the Battlemap toolbar, saved in `Scenes.AmbientVisualDistance`, and it is kept when the grid or background changes. The **Visual Distance** belongs to the character: it is the **Light (m)** field in the Traveller dialog (renamed on screen from Visual Distance), saved in `Characters.VisualDistance`, and it is shown as "Light" under the stance in the Combat Actions panel when the selected combatant is a Traveller. The Traveller sees as far as **the higher of the two** (`LineOfSight.SightMetres` in `MTU.Core`, `sightRangeSquares` in `wwwroot/js/LineOfSight.js`), at 1.5 m per square, so 24 m is 16 squares. **When both are 0 nothing is cleared by sight and the GM reveals the map by hand**, which is how every existing scene and character starts. The VisualDistances migration adds the two columns at 0 and changes no other data; rolling it back drops them. Patrons, Enemies and animals share the `Characters` column but have no field for it, because only Travellers reveal. A reveal happens when the selection changes, when that Traveller's token is placed or its move is saved, when either distance changes, when a polygon change is saved, and when fog is switched on. Only a Traveller on the map reveals: selecting a Patron, Enemy or animal reveals nothing, so an enemy's turn never uncovers the map. A square is seen when its centre is within the sight range of the centre of the Traveller's square, is not inside an active polygon, and the straight line between the two centres is clear (`visibleSquares` and `sightClear`). Active polygons are solid: sight does not pass through the inside of one, a square whose centre is inside one is never revealed, and a Traveller standing inside one sees nothing. Inactive polygons are ignored, so clicking a door polygon open reveals what is beyond it at once. Touching one polygon's corner or running along one polygon's side does not block, but a line squeezed between polygons that touch at a corner or share a side is blocked, so there is no seeing through a gap of no width. Seen squares stay seen: fog is only ever cleared by sight, there is no per-character visibility, and the result is the scene's ordinary fog state. Each reveal is applied and saved exactly like a fog stroke (`revealSight` in `wwwroot/js/Battlemap.js`), so it reaches players only once stored, Undo fog takes it back, and a failed save puts the fog back. A reveal happens once per situation, meaning the same Traveller on the same square with the same range and polygons, so Undo fog or Ctrl+drag over squares in view is not overridden until something changes; selecting someone else and coming back counts as a change. Nothing is revealed while a token is being dragged or its move is being saved, and a reveal that comes due while fog is being painted or saved waits until that has finished. Manual fog editing works as before. No snapshot field was added: players receive only the revealed squares, as with painted fog, and never the polygons, the distances or anything about the sight calculation (`playerTokens` copies only named fields, so a token's Visual Distance stays with the GM). A visible token standing on a newly seen square appears to players as it would on any revealed square. One visible side effect: a Traveller's own token is hidden from players while it is dragged across fogged squares, and reappears when the move is saved and the fog clears. ## Injury Tolerance

A Traveller, Patron or Enemy, or animal can have any number of Injury Tolerance records, stored in the `CharacterInjuryTolerances` table (one row per record, in `Sequence` order, deleted with the character). Each record is an `InjuryTolerance` flag value: one or both effects (**Halve Injury**, **Minus 1 per D**) and the damage types it covers. The services' `Character.InjuryTolerances` list carries them, and saving replaces a character's records with the list given, dropping records with nothing ticked. A character can have up to 20 records.

**Damage types.** Kinetic matches any melee attack and Gun Combat (Slug) weapons. Energy matches Gun Combat (Energy) weapons. Laser matches a ranged weapon with the word "Laser" in its name, and **Disruptor** matches a ranged weapon with the word "Disruptor" in its name, the same way. Psionic is reserved and matches nothing yet. A record applies when any of its types matches, and counts once even when several match.

**Stacking.** Every record that matches the attack adds its effects (`InjuryToleranceRules.Applicable` returns an `InjuryToleranceEffect` with the total per-die reduction and the number of halvings). After armour, the per-die reductions are all taken off first (two Minus 1 per D records take 2 per damage die), then the injury is halved once per Halve Injury record, rounding down each time; it never goes below 0. This order is marked as a `RULES-ASSUMPTION` in `InjuryTolerance.cs`. The Attack Resolution dialog shows the stacked total, such as "Minus 2 per D (3 dice), Halve Injury ×2". Saved attack outcomes now store the stacked effect (`AttackOutcome.ToleranceEffect`); an outcome saved before this change still uses the single tolerance it stored.

**Editing.** `InjuryToleranceEditor` shows each record as a numbered row of chips (effects, then "vs" and the damage types) with a × to remove it, and an Add Injury Tolerance link. A record missing an effect or a damage type is marked and has a hint, because it can never change an attack.

**Migration.** `20261122040000_InjuryToleranceRecords` creates the table, copies each character's non-empty single `Characters.InjuryTolerance` value into its first record unchanged, then drops the column. Rolling back adds the column again and merges each character's records into one value (every option ticked on any record), without Disruptor, which did not exist before.

Checks: `MTU.RuntimeChecks/InjuryToleranceChecks.cs` covers the type filters (including Disruptor), stacking and its order, the description, validation and empty records, persistence for Travellers, NPCs and animals, deletion, the migration from the single value and its rollback, attacks with several records, and older saved outcomes. `AnimalCombatChecks.cs` checks that the tracker carries an animal's records into combat.

## Careers

Travellers and Patrons and Enemies each have a career: an ordered list of four-year **Terms**, edited on the Career tab of their dialog. Animals have none. A career starts at age 16, so term N starts at age 16 + 4 × (N − 1).

Each term records a **Service** and three checks, each stored as passed or failed: Survival, Advancement and Commission, plus free-text Notes about what happened in the term. The service is one of Agent, Army, Citizen, Drifter, Entertainer, Marine, Merchant, Military Academy, Navy, Noble, Rogue, Scholar, Scout, University or Prisoner, or Other with a name typed in (the typed name is what is stored). Army, Marine, Navy and Military Academy are the military services. Not every term has every check:

- **Commission Check:** military services only, and only once in a character's whole military career. Once one term holds a passed Commission Check, the box is disabled on every other term.
- **Advancement Check:** every service except University and Military Academy, which are study rather than service. It is also unavailable in the term that holds the passed Commission Check: the commission is checked first, and a character cannot be promoted twice in one term.
- So University has neither, and Military Academy has a Commission Check but no Advancement Check.

A check a term doesn't have is disabled in the editor and saved as not passed (`CareerServices.HasAdvancement`, `CareerRules.CommissionAvailable`). University shows no rank either. Life events, career events and mustering out are not tracked.

**Rank** is worked out from the terms, not stored (`CareerRules.Rank` in `MTU.Core/Career.cs`). Each passed Advancement Check adds one rank. A military recruit starts at E-0; a passed Commission Check ends enlisted advancement and starts officer rank at O-1, and advancements in later terms raise officer rank. The commission is the only promotion in its term, so an Advancement Check recorded in the same term is ignored. The **highest rank** in a military service is the larger of the enlisted and officer numbers, not their sum, so E-4 followed by a commission is still 4 and reads as E-4 until the officer rank catches up.

**Military rank transfers between the military services.** Enlisted and officer rank are counted over all of a character's military terms in order, so someone who leaves the Army at O-2 starts the Navy at O-2, and a commissioned Military Academy graduate starts the Navy at O-1 and is O-2 after a first Navy term with a passed Advancement Check. The rank in a particular military service is the rank held at the end of the last term served in it, and 0 if the character never served in it. Military Academy rank is displayed like any other ("Military Academy O-1"), so a graduate who never enters a military service still shows the commission as their highest military rank. Rank does not transfer to or between the other services. Each of those keeps its own rank, starting at 0 and counted over that service's own terms, even when they aren't consecutive.

The Career tab lists the terms with term number, starting age, service, the Survival Check, a Promotion column and the rank held after that term. Promotion combines the Commission and Advancement Checks (`CareerRules.PromotionInEachTerm`): "Commissioned to O-1" for the term that holds the commission, "Promoted to E-2", "Promoted to O-3" or "Promoted to Rank 1" for a passed Advancement Check, and blank when neither passed or the term has neither check. A promotion names the rank just gained, so a new officer's first advancement reads "Promoted to O-2" even while the Rank column still shows a larger enlisted number. Military ranks are written with a hyphen (E-2, O-1) everywhere they are shown. The editor keeps the three checkboxes in the order they are rolled: Survival, Commission, then Advancement. A term's notes appear as muted text in a second row under it, spanning the table except the Edit and Delete buttons. Above the table, a heading names the service of the latest term, followed by the number of terms, the years served (four per term) and the highest rank in each service where the character holds one. Term numbers are shown as two digits (01, 02). Terms are added and edited in their own dialog (`Components/SheetDialog.razor`, a small modal in the sheet style with the title as the red bar): **+ Add term** at the right of the career heading opens it for a new term at the end of the career, and a row's Edit opens it for that term, whose row stays highlighted behind it. Save closes it; Cancel or Escape discards the changes. A new term starts in the same service as the last one. There is no reordering. Delete asks for confirmation, and later terms move up one, which changes their ages. Terms save as they are changed, like skills and equipment.

**Age and Birthday.** Every character has a Birthday, a day of the year from 1 to 365, default 1. A Traveller with N terms is 16 + 4N on day 1 of 1105 and is a year older on each birthday after that, using the campaign's current year and day (`CharacterAge.Calculate`). A Traveller with no terms is 16. Patrons and Enemies keep their own stored Age; their Birthday and career are recorded but don't change it.

**What replaced what.** The Terms Served text and the stored Highest Naval Rank and Highest Scout Rank are gone. The Travellers table has a Terms Served column with one line per service in order of first term, giving the terms and the highest rank there (`CareerRules.ServiceLines`): "3 Terms in Navy (O-2)", "1 Term in Scout". A rank of 0 is left out. The calculated age is a muted second line under the Race. The mail DM for the highest Naval or Scout rank on board (`CharacterService.MailModifiersAsync`) now uses the highest rank in Navy and in Scout from each active Traveller's career.

**Migration.** `CareerTerms` adds the `CareerTerms` table (cascade-deleted with its character) and `Characters.Birthday`, converts existing data, then drops `TermsServed`, `HighestNavalRank` and `HighestScoutRank`. Each comma-separated entry of the old text becomes that many terms: "Navy 3, Diplomat 1" gives three Navy terms and one Diplomat term. Listed services get their listed spelling (common plurals such as "Scouts" too), anything else is kept as an unlisted service, a plain number becomes terms in a service called Unknown, a name with no number counts as one term, and one entry is capped at 20 terms. Converted terms are marked as survived. The stored ranks become passed Advancement Checks on the first Navy and Scout terms. A rank higher than the number of terms in that service can't be reproduced, so it is written into the first term's notes; a rank on a character with no terms at all is lost. Rolling back rebuilds the text and the two ranks from the terms, but notes, Survival and Commission Checks, and the order of interleaved services can't be kept.

Checks: `MTU.RuntimeChecks/CareerChecks.cs` covers the rank rules (enlisted, commission, officer, both checks in one term, larger-of-the-two, transfer between military services, the Military Academy rank, the single commission, the promotion text for each term, the Terms Served lines, services with no Advancement Check, and separate ranks for the other services), ages and birthdays, saving, editing, deleting and renumbering terms, validation, campaign isolation, animals, cascade deletion, the mail rank, and the migration in both directions.

## Traveller dialog

Add Traveller and Edit on the Travellers page open one popup dialog, `Components/Pages/TravellerDialog.razor` (a native `<dialog>` opened through `wwwroot/js/EquipmentDialog.js`). Escape closes it through the dialog's own `cancel` event; a `cancel` that bubbles up from a file input inside it (the token picker being dismissed) is ignored (`isDialogCancel`, covered by `Components/EquipmentDialog.test.mjs`), so dismissing the picker no longer closes the dialog. Every dialog opened through that module gets the same fix. It replaces the inline editor and the separate Skills and Equipment panels on that page, so the table rows now only have Edit and Delete.

The upper part holds the Traveller's details. The UPP is edited as six number fields, STR, DEX, END, INT, EDU and SOC, each 0 to 33. It is still stored as one UPP text value, so there is no migration: `MTU.Core/CharacteristicProfile.cs` splits it into scores and joins them back as eHex digits. An empty field is an unknown score. Six empty fields save an empty UPP; otherwise an unknown score is written as `?`, which every reader already treats as not recorded. Digits after SOC, such as PSI, aren't shown but are kept. If no score is changed, the stored UPP text is saved back untouched.

The details also hold the Birthday (day of the year). Terms Served and the Naval and Scout ranks are no longer entered here; they come from the Career tab.

**Character sheet style.** The Traveller and Patron/Enemy dialogs are laid out as a character sheet. The look is a set of global classes in `wwwroot/app.css` under `.sheet` (put `sheet` on a dialog to use it), so other dialogs and tables can move to it one at a time: square dark panels, a red section bar (`.sheet-bar`), small monospaced capitals for labels (`.sheet-label`), and a condensed face for names and numbers (Bahnschrift Condensed, which ships with Windows, falling back to other condensed fonts; no web font is loaded). Fields are ordinary inputs styled as text (`.sheet-input`), so the sheet stays editable: an underline shows on hover and turns red on focus. Inside a `.sheet`, Bootstrap tables, primary buttons, checkboxes and `TabBar` tabs take the sheet colours. The sheet has three numbered sections:

- **01 / Personal Data.** A red bar, then Name (large), Race, Age and Player; under a rule, Birthday, Speed, Light, Natural DR and an Inactive switch; then Description and the [Injury Tolerance](#injury-tolerance) records (each drawn as a row of chips); and the token in a round frame at the right with Add/Replace token and Remove token. The Traveller's Age is worked out as on the Travellers table (`CharacterAge.Calculate`) from the campaign date, the career terms and the Birthday, and follows the Birthday as it is typed; it is read-only. The Combat Tracker's Edit opens the dialog without the campaign, so the dialog looks the campaign up itself. **Light** is the new name on screen for the Traveller's own Visual Distance (see [Line-of-sight fog](#scenes-and-battlemap)); it is the same `Characters.VisualDistance` value, so there is no migration. The Patron/Enemy sheet has Name, Race, Age (its stored age) and Gender on the first row, then NPC Type, Skill Level, Occupation, Birthday, Speed and Natural DR, then Quirks 1 and 2. A locked NPC field (type, skill level, occupation and race once the NPC exists) shows as plain text without the drop-down arrow.
- **02 / Characteristics.** `Components/CharacteristicCards.razor`, shared by both dialogs: the Universal Personal Profile as text at the right (it follows the scores as they are typed), and one card per characteristic with its code, the score as a large editable number, the full name and the characteristic DM in a box (`Encounter.Dm`). STR, DEX and END also have a smaller **Now** box in the middle of the card with the current value after damage, teal when it equals the score and amber when it is lower. It comes from the Combat Tracker (`SceneService.CurrentCharacteristicsAsync`): a Traveller has one token, which moves between scenes, so its scene's saved encounter state gives its current STR, DEX and END; an older scene that stored only a hit point total is spread over the three as the Combat Tracker does. With no damage recorded, or no token, Now equals the score. A Patron or Enemy placed more than once has no single value, since each instance is hurt on its own, so Now shows a dash. Now is read-only on the sheet; damage is still changed in the Combat Tracker. INT, EDU and SOC have no Now box.
- **03 / Service record.** The Career, Skills, Armour and Weapons tabs, each with a count badge (`CharacterService.RecordCountsAsync`, refreshed after every change made on a tab). The tabs are drawn only once the counts and current values have loaded, so the dialog and its tabs never query the shared database context at the same time.

**The rest of the app follows the sheet.** The `:root` palette in `app.css` now uses the sheet colours (the `--sheet-*` variables, which the `--app-*` variables point to), so every page, panel and the Cast view take the dark panels, 2 px corners and red accent. Primary and outline-primary buttons are red, checked boxes are red, page titles (`h1`) use the condensed face, and tabs in every `TabBar` are square with the open tab in red. Bootstrap tables everywhere have monospaced capital headings, and buttons inside any `.table` are compact (smaller padding and font) so rows stay short. The Animals and Creatures dialog is a full sheet like the others (01 / Creature Data with the token column, then the Skills and Attacks tabs with count badges). The smaller dialogs (catalogue equipment, equipment options, delete confirmation, attack resolution, campaign, pre-engagement and sector refresh) use `sheet sheet-dialog` with a `sheet-title` heading, which turns the title into the red bar across the top; their own layouts are unchanged. Inside any `.sheet`, a label that holds a form control reads as a small monospaced capital caption while the control keeps the normal font. The Combat Description dialog, which players also see, keeps its layout and takes the new colours only.

Patrons and Enemies now have a Natural DR field; `NpcService.SaveAsync` saves it and rejects a negative value. Before, NPCs always kept 0. There is no migration, since the column already existed.

Checks: `MTU.RuntimeChecks/CharacterSheetChecks.cs` covers the record counts, the current values (none, one token, damage from the encounter state, a hit point total from an older scene, several NPC instances, campaign isolation) and NPC Natural DR. The layout itself is Razor and CSS, so check it in the browser.

The lower part is a [tab bar](#tabbed-pages) with Career, Skills, Armour and Weapons, opening on Career (a newly generated NPC opens on Skills, because it has no career until it is saved). Career lists the character's [career terms](#careers). Skills is the existing skills panel, and Armour and Weapons are the existing equipment panel limited to one category (`CharacterSkills` with `Embedded`, `CharacterEquipment` with `Kind`); both drop their own heading, Close button and frame inside the dialog. The catalogue and options dialogs open on top of the Traveller dialog.

Save and Close sit in the dialog header. Save applies to the details only; skills and equipment save as they are changed, as before. Close or Escape discards unsaved detail changes. Saving an existing Traveller closes the dialog. A new Traveller has no skills or equipment tabs until it exists, so Add Traveller saves it and keeps the dialog open with the tabs unlocked (`CharacterService.SaveAsync` now returns the Traveller's ID). The Traveller table behind the dialog reloads after every save.

**Patrons and Enemies** use the same layout in `Components/Pages/NpcDialog.razor`, opened by the Ally/Enemy, Patron/Civilian and Combatant buttons and by Edit; the table rows there also only have Edit and Delete now. The details add the NPC fields (NPC Type, Skill Level, Occupation, Race, Gender, Age and Quirks), and the generator behaviour is unchanged: on a new NPC, changing type, skill level, occupation or race rerolls as before, and those four are locked once the NPC exists. A new NPC's skills and Combatant loadout are generated with it, so before it is saved the Skills, Armour and Weapons tabs show what was generated, read-only. Add Character saves it with those skills and that equipment and keeps the dialog open with the tabs editable (`NpcService.SaveAsync` also returns the ID).

**Animals and Creatures** use `Components/Pages/AnimalDialog.razor`, opened by the Killer, Hunter and Prey buttons and by Edit; the table rows only have Edit and Delete. Animals have no characteristics, no career history and no armour or weapons, so the details are the animal fields (Name, Animal Type, Behaviour, Traits, Hits, Speed, Shared, Description, Injury Tolerance and token) and there are two tabs: Skills and Attacks. Attacks is the existing natural attacks panel (`AnimalAttacks` with `Embedded`); natural attacks are used in combat like any other weapon. A new animal's skills are generated with it and shown read-only until Add Animal saves it and keeps the dialog open. `AnimalService.SaveAsync` replaces an animal's skills and attacks with those on the record it is given, so the dialog re-reads the stored animal after every skill or attack change and again just before saving details; otherwise a details save would undo changes made on the tabs. It now returns the character ID too.

**Combat Tracker.** The Combat Actions heading has Describe and Edit; Edit replaces the earlier Skills and Equip buttons. Edit opens the selected combatant's own dialog from above: the Traveller, Patrons and Enemies, or Animals and Creatures dialog, so it is also available for animals. It edits the stored character, so it shows the character's name rather than a tracker instance name, and a change applies to every instance of that character. After each save in the dialog (details, a skill, equipment or an attack) the tracker reloads its roster and that character's loadout. The dialog is rendered only on the GM's Battlemap page and adds nothing to the player snapshot, so it never appears in the Cast view. Describe is unchanged and is still shown to players. The earlier `CombatSkillsDialog` and `CombatEquipmentDialog` components have been removed.

Checks: `MTU.RuntimeChecks/CharacteristicProfileChecks.cs` covers splitting and joining the UPP, unknown scores, PSI digits, the 0 to 33 limits and the ID returned by a save. The dialog itself is Razor markup, so verify it in the browser.

## Tabbed pages

The Supply Catalog (Armour, Weapons), Passengers and Cargo (Passengers, Freight) and the Traveller dialog use one shared component, `Components/TabBar.razor`. It draws the tab buttons, an optional `TabBadge` beside each label (the character sheet uses it for counts), an optional `Extras` area at the right of the bar for controls or badges that belong to the open tab, and a single tab panel. The page supplies the panel content and switches it on the active tab, so only the open tab is rendered. Anything the hidden tab needs to keep lives in the page's fields. Left and Right arrow keys move between tabs. The open tab isn't remembered: each visit starts on the first tab.

The Cover Protection page uses the same header, editor panel and bordered table as the other list pages, with the editor above the table.

This is UI only, with no schema or service changes. No automated check covers it, so verify it in the browser.

## Delete confirmation

Travellers, Patrons and Enemies, Animals and Creatures, Scenes, Cover Protection and the Armour/Weapons catalogue all confirm deletion with one shared modal, `DeleteConfirmDialog` (a native `<dialog>` opened through `wwwroot/js/EquipmentDialog.js`). It names the item, offers Cancel and a red Delete button, and closes on Escape. While the delete runs, both buttons are disabled. If it fails, the dialog stays open and shows the error.

Animals and Creatures previously deleted without asking. If the animal is Shared, the dialog warns that it's used across multiple Campaigns and that deleting it removes it from all of them, which matches `AnimalService.DeleteAsync`. The Cover Protection and Equipment editors no longer have a delete mode; they only add and edit.

This is UI only, with no schema or service changes. No automated check covers it, because Razor markup isn't exercised by the RuntimeChecks, so verify it in the browser.
