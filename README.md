# MTUAssistant

The home-page atlas is drawn directly from the M1105 sector/world database using PixiJS and pixi-viewport. Imported political borders and routes render above the grid using their stored colours. Downloaded PNG tiles are not required by the map. Refresh Sector Data downloads system data and TravellerMap metadata instead.

## Map detail

Detail switches according to CSS pixels per parsec (not device pixel ratio):

| Zoom | Detail |
| --- | --- |
| Below 10 | World circles and borders; no routes, world names or hex grid |
| 10–below 25 | World circles and hex grid; subsector capital (Cp) names only |
| 25–below 55 | World circles, hex grid, gas giants, bases and travel-zone rings; starport class; names for capitals and population 9+ |
| 55–below 95 | World circles, hex grid, gas giants, bases and travel-zone rings; full UWP and every world name |
| 95 and above | All details, including hex coordinates |

Map label fonts are 20% smaller at all zoom levels below 95 px/pc; full-detail fonts at 95+ are unchanged. Sector and subsector boundaries draw at every zoom. Label eligibility follows fixed bands in `wwwroot/js/MapGeometry.js`; no collision rejection, text budget, or zoom history suppresses eligible labels. Only off-screen text is culled. Subsector capital names are red; population 9+ names are uppercase (high-population eligibility uses 9+). Sector names remain visible, with subsector region names from 25 px/pc.

At close zoom, UWP sits at the top of the hex, below coordinates when shown; names have a four-pixel bottom margin. World circles grow with zoom. Zone rings have a minimum 2 CSS pixel stroke at every zoom level where they are displayed. Amber/red zone rings are fully opaque and do not affect symbol positions. Naval and scout symbols sit at upper/lower left; the gas giant is inset at upper right, aligned with the naval symbol. Click a marker or hex to select it; drag to pan. The viewport is remembered between visits. Selecting a system in the search dropdown (mouse or Enter) opens the map, pans smoothly to and highlights its hex at the current zoom (650 ms, with reduced-motion support), and loads the same details panel as a map click. Selecting a sector or subsector pans to its centre with the same animation, clears the world highlight and details, and preserves zoom. Search links use a stable target ID and a request token so selecting the same world again recentres it. Requests made while the map is loading are applied when it is ready; systems outside M1105 show an availability message.

`GET /api/map/overview` supplies sector metadata, world positions and compact world name/UWP/remarks data so zoomed-out capital labels are available immediately. The browser fetches detailed map attributes from `GET /api/map/sectors/{id}` for nearby sectors, with bounded concurrent requests and a client-side sector cache; these endpoints read cached server projections, not the database. Map descriptions and data projections live in MTU.Core; rendering geometry and detail thresholds live in `MTUAssistant/wwwroot/js/MapGeometry.js`.

## Shared system catalogue

After database migration, application startup awaits the singleton `SystemDataProvider.InitializeAsync()` before accepting requests. It loads sectors, subsectors, allegiances and systems once, using a short-lived database scope, and publishes a complete immutable `SystemCatalogue`. Concurrent initialization callers share the same task; a failed load prevents startup rather than exposing partial data. After a refresh, the provider reloads and atomically publishes a complete replacement snapshot; a failed reload leaves the prior snapshot available.

`SearchService`, `MapDataService` and `WorldSelectionService` share that catalogue across requests and Blazor circuits. Search retains its existing all-milieu scope, result grouping/limits and subsector context. Map and selection retain the M1105 filter. Map overview and per-sector DTOs are rebuilt when the catalogue changes, preserving existing API response shapes. Search returns fresh UI result objects so edits cannot affect shared data.

`CatalogueSystem` owns a stable system ID, location, `MainWorldData` and an immutable `Bodies` collection. Main-world data retains all currently stored system attributes. Bodies are currently empty; future `SystemBodyData` record types can supply stars, planets, moons and orbital information for an orrery without changing search or map contracts. No bodies or orbital positions are inferred from summary counts. Add future body-table loading to the provider's startup load and publish it as part of the same snapshot.

The runtime checks initialize concurrently, verify one read per source table, then close the test database and exercise search, map and selection. They also cover empty catalogues, milieu filtering, cancellation and protection from mutable search results.

## Refreshing sector data

Refresh Sector Data updates every sector in the configured M1105 area. For each sector it retrieves system data and TravellerMap metadata before replacing the sector's names, subsectors, allegiances, systems, borders and routes in a single database transaction. Existing sector IDs are retained. No sector or subsector image tiles are downloaded. A failed download leaves that sector's previous data intact and is counted in the progress dialog; cancellation retains already committed sectors.

Border paths and route endpoints (including cross-sector offsets) are preserved. Explicit colours take precedence over matching TravellerMap stylesheet rules; the original stylesheet and metadata fields are retained for future rendering. After a completed, cancelled, or interrupted refresh, the shared catalogue reloads any committed sector updates; open maps reload their data and clear their selection.

## Trading

Select a world on the map, then open Trading. Broker and Streetwise generate and save independent markets for each sector and hex. Common and matching goods use their listed lot sizes; extra D66 rolls add lots to existing entries. Broker rerolls illegal goods; Streetwise marks randomly rolled legal goods as stolen. Exotic goods have referee-determined tonnage. Each purchase price per ton uses a 3D roll, the saved skill DM, the strongest matching purchase DM and the strongest matching sale DM subtracted. The supplier DM is entered as a signed modifier and defaults to −2. Existing priced markets retain their original prices until rerolled. The resulting percentage and prices are saved with the market. Existing markets receive prices once on first opening without changing their goods or quantities. Markets survive system-row replacement during sector refresh.

Buying and Selling each have an independent active Traveller dropdown followed by mode controls. Each displays the selected Traveller total DM: Broker or Streetwise skill level plus the higher INT or EDU DM of the same Traveller. Missing skill uses the untrained -3 penalty reduced by the same Traveller's Jack-of-All-Trades level, to a minimum penalty of zero; skill zero is trained and receives no Jack-of-All-Trades bonus. This also applies to untrained Steward passenger modifiers. Jack-of-All-Trades does not grant Steward training or enable High passage. Unknown trading INT or EDU defaults to score 7 (DM 0), equivalent to UPP 777777 when the whole profile is unknown; the stored UPP is unchanged. Select a Traveller separately for each panel; Skill DM is blank and rolling is disabled until an active Traveller is selected. Buying and Selling Traveller and mode selections are remembered independently per campaign during the current user session, including navigation away from Trading. Inactive or deleted selections are cleared on reload. Modifiers refresh before each roll; saved markets retain the DM used when rolled. Current and destination worlds display UWP badges on the left and trade codes and travel zone badges on the right, matching Freight. Selling (Imports) can use the current world or an alphabetically sorted destination within six parsecs. Remote worlds load or generate their own saved selling market and show a red seven-day-old price badge. Selling lists goods with a positive matching Sale DM. Broker also includes common goods and excludes illegal goods; Streetwise excludes common goods and can include illegal goods. Roll calculates the sale price per ton from 3D plus the Selling section’s selected skill DM and strongest Sale DM, minus the strongest Purchase DM, plus the signed Buyer DM (default −2). Demand in tons is rolled using each commodity’s listed tonnage dice. Older saved Imports receive demand once without changing their prices. Sale results are saved independently by world and mode and marked outdated when reopened. They are sorted from highest to lowest price percentage.

The D66 goods, availability codes and lot sizes are based on [Trade Goods Dice Modifiers](https://github.com/timtoon/trade-goods) by Tim Heiderich (Mongoose Traveller 2nd edition, 2016); the aid identifies itself as CC BY-NC 4.0. Its ice-world availability codes have been normalized to TravellerMap's `Ic` code.

## Equipment

Equipment contains a shared database-backed catalogue of Armour and Weapons. Add, Edit and Delete use the same native modal dialog available from Traveller equipment. Armour and weapon notes appear in a muted Notes column. Range is numeric, nonnegative metres and accepts fractional values; tables display it as `<Range> m`. Damage, magazine, required skill and traits are text fields to allow rulebook notation; weights and credit costs accept decimals.

Open a Traveller's Equipment panel to select catalogue items and add or remove them. New Equipment opens the shared dialog and selects the newly saved item, ready for Add Equipment. Each catalogue item can be assigned once to each Traveller. The Traveller table shows comma-separated summaries: `Name (protection)` for armour and `Name (rangem, damage)` (compact metres in Traveller summaries) for weapons. Editing an assigned item updates the shared catalogue for all Travellers; removing it from a Traveller leaves the catalogue intact. Deleting a catalogue item confirms that it will also remove all assignments. Deleting a Traveller or campaign removes its assignments and preserves the catalogue.

The Equipment migration runs at application startup and retains existing campaigns, Travellers, skills and equipment-independent data. Runtime checks cover field persistence, summary formatting, assignment isolation, duplicate and invalid input handling, shared edits, removal, and cascading deletion.

### Traveller equipment options

Traveller equipment assignments store Quantity (minimum 1) and optional Scope, Targeting System, Laser Sight, Holographic Sight, FOF, PHUD and Smart Tracker flags. Existing assignments migrate to quantity 1 with no attachments. These settings are independent for each Traveller and do not modify the shared catalogue. Add Equipment opens a second dialog before the assignment is saved; Options reopens it for an existing assignment. Cancel leaves the saved assignment unchanged.

Attachments are available only for weapons whose numeric Range is greater than zero; range zero is treated as melee. Smart Tracker implies Intelligent Weapon. Quantity appears in both Traveller equipment tables. Weapon attachment summaries appear in secondary text beneath catalogue Traits, using labels such as `Scope, Laser Sight, PHUD`. Weight and credit columns retain their catalogue values per item.

## Sector Data view

The Refresh Sector Data navigation item opens `/sector-data` without starting a refresh. The page reads database counts for sectors, sector names, subsectors, systems, allegiances, borders and routes, and lists loaded milieus. Refresh Sector Data Now runs the original refresh action and progress dialog. While a refresh is running the button can reopen its progress dialog. Statistics reload after completion, cancellation or failure so any committed partial updates are reflected.

A completed refresh stores its real UTC completion timestamp in the database. The Last Refresh badge displays that date in the browser's local time as yyyy-MM-dd, with the full local timestamp on hover. Cancelled or faulted refreshes retain the previous completed timestamp. A completed run may include individual sector failures, as reported by the existing progress dialog. Until a refresh is recorded, the badge displays Not recorded. Counts use an independent database scope and a read transaction to avoid sharing the refresh worker's DbContext.

### Population statistics

Sector Data includes total known main-world population for loaded charted space and the ten largest populations by major polity, followed by Others. Rows show exact whole-person totals and percentage shares. The first two letters of allegiance codes define the major polity, case-insensitively, across sectors within one milieu. All Im* allegiances aggregate as Third Imperium (Im). Other names use two-letter metadata when available, a common recorded family name, or the prefix as a fallback. Unknown allegiance is retained as Unspecified polity. If several milieus are loaded, a selector keeps their populations separate and defaults to M1105 when available.

Population follows Traveller Map Second Survey: PBG population multiplier times 10 raised to the UWP population exponent. A zero multiplier with a positive exponent uses the documented legacy multiplier of one. Unknown or invalid population data is excluded and reported as a system count; no population is inferred for other system bodies. Decimal arithmetic avoids aggregate 64-bit integer overflow. The top ten plus Others reconcile exactly with the displayed total, and refresh completion recalculates the figures from the database. Source: https://travellermap.com/doc/secondsurvey#population-exponent

## Patrons and Enemies

The campaign-specific `/patrons-enemies` view supports adding, editing and deleting characters with token image, name/occupation, race/gender, two quirks, UPP and skill level. Occupation, gender and Quirks 2 use secondary styling beneath their primary values. Generated UPP uses type, racial and skill-level adjustments and displays in uppercase. Skill level offers 12 numbered ratings: Recruit, Novice (default), Adept, Practitioner, Veteran, Expert, Master, Elite, Champion, Hero, Mythic and Legendary. The generation buttons create reviewable drafts. Before the first Save, changing occupation or skill level rerolls draft skills. Saved NPCs lock type, occupation, race and skill level so these fields cannot trigger regeneration.

Skills and Equip reuse the same inline editors and catalogue dialogs as Travellers, including token headers, named/specialised skills, armour-specific protection, quantities, attachments, and worn/equipped state. NPCs use explicitly classified character records with a one-to-one NPCs profile so these existing editors and relationship tables remain shared. Player Traveller listing, mail/passenger modifiers and party trading exclude NPCs; player character save/delete operations reject NPC IDs. Patron/enemy operations are restricted to the current campaign and cannot edit player characters. Deleting an NPC cascades its profile, skills and equipment assignments while preserving catalogue items. Existing characters migrate as player Travellers.

### Character schema naming

Shared records use Characters / CharacterEntity and CharacterService. NPCs / NpcEntity stores the one-to-one NPC profile, with NpcService providing NPC operations. CharacterSkills and CharacterEquipment use CharacterId foreign keys; the shared character name is Name. Shared editors and helpers use Character naming. The Travellers and Patrons and Enemies screen names remain unchanged. The CharacterNaming migration renames populated tables and columns in place, preserves IDs and relationships, and supports rollback without deleting character data.

## Map presentation

On the Home map, the cast icon (**Present map**) opens a separate read-only map window. Move it to the presentation monitor and use the browser's fullscreen command (F11 on Windows). It follows the Admin map's centre, zoom, search navigation and selected hex. A different window size shows more or less surrounding space at the same map scale. Admin navigation and campaign controls are omitted. The shared System Data panel follows the selected hex and displays the world heading, UWP, trade codes, travel advisory and stellar details; deselection clears it. Presentation clicks and drags do not change the map, while its details panel can be scrolled.

Each Admin tab keeps a presentation session in browser session storage. Map snapshots are sent through a named BroadcastChannel and cached locally for late opening, reload and reopening. Only map camera coordinates and selection are shared; the presentation loads the selected world details from the same local catalogue. This initial version requires both windows in the same browser profile and application origin; it does not synchronize to another browser or device. Leaving Home freezes the last presentation snapshot; returning resumes updates. No database migration is required. The view is read-only UI, not an authentication boundary for other application routes.

Presentation checks: `node MTUAssistant/Components/Map/PresentationSync.test.mjs` and the existing map geometry/selection checks.

The Presentation map also shows the Admin pointer as a 25 CSS-pixel, semi-transparent light-blue circle. Pointer positions use map coordinates so they align across different window sizes and zoom levels. The marker hides when the pointer leaves the Admin canvas, its window loses focus, Home is left, or the location is outside the presentation viewport. Pointer updates are transient and are not saved with the cached map snapshot.

### Random NPCs

Ally/Enemy rolls D66 on the original 36-type occupation table, D6 for race (1-3 Human, 4-5 Aslan, 6 Vargr), and D6 for gender (1-3 Male, 4-6 Female). Choose Skill Level beside the generation buttons before generating (default Novice). Recruit through Legendary represent levels 1-12 and receive two skill rolls per level (2-24 rolls). Each profession has eleven distinct catalogue skills indexed by unmodified 2D6 totals 2-12. Core skills sit near 6-8 (especially 7), with background skills toward 2 and 12. The first acquisition gives rank 0; each duplicate increases the rank by one, up to rank 5 (six acquisitions). Further rolls of a capped skill are rerolled until another skill is selected, without consuming the acquisition budget. The number of distinct skills can be smaller than the roll count. Pools use the existing catalogue and always specify a speciality for skills that have them, such as Electronics (Computers), Athletics (Dexterity) and Gun Combat (Slug). Different specialities of the same base skill can appear in a pool. Acquisitions and the rank-5 cap are tracked independently by full speciality name. When saving, each acquired speciality also records its base skill at rank 0; speciality entries are recorded only at rank 1 or higher. Multiple specialities share a single base entry. The draft preview shows this recorded form while retaining the full acquisition history until Save.

The draft previews generated skills. Changing skill level in a generated draft rerolls its skills, age and UPP. Names, UPP and quirks are generated and remain editable. Name remains editable before and after saving. Nothing is written until Save; Cancel discards the draft. New NPC profiles and generated skills save atomically. Saved profile edits leave generated properties unchanged; skills remain separately editable through the Skills panel. Age is rolled as 16 + 4 × level + D6 - 3 (maximum 67 at level 12), displayed in the list and editable in the draft. The NpcAge migration adds a nullable age column at startup; existing NPC ages remain unknown. Deterministic generation and database checks are included in MTU.RuntimeChecks/NpcGenerationChecks.cs.

### NPC types and filtering

NPCs persist a type selectable before the first Save: Ally/Enemy, Patron/Civilian or Combatant, displayed in the list. The NpcType migration adds the type column at startup and classifies pre-existing NPCs as Ally/Enemy. Ally/Enemy uses the original archetypes. Patron/Civilian uses all 36 occupations from the supplied Random Patrons D66 table, each with eleven specialised catalogue skills arranged around the 2D6 bell curve. Combatant uses a shared military grunt pool and starts with Occupation Unspecified; Gun Combat (Slug) sits at 7, with Leadership at 2 and Tactics (Military) at 3. All types use the selected skill level, existing race/gender/age rolls, rank-5 cap, independent specialities and base-skill recording rules. No draft is stored until Save. The Add Character button is removed: start with a generation button at the chosen skill level. In the editor, NPC Type appears before Occupation and determines its alphabetised profession choices. Changing type or occupation rerolls skills while preserving age; changing skill level rerolls skills, age and UPP. Combatant professions include Guard, Marine, Mercenary, Militia, Scout, Security Officer, Sniper and Soldier, sharing the grunt pool. Existing custom occupations are retained in the read-only saved profile. Cancel discards all rerolls; Save atomically replaces the previous skills when rerolled.

Filter NPCs searches Name, Occupation, Race, skill-level name/number, and skill names/ranks case-insensitively as text is entered. NPC type labels are searchable as well. Clear restores all campaign NPCs; no matches show a dedicated empty state.

### NPC UPP generation

Roll six lots of 2D6 for STR/DEX/END/INT/EDU/SOC. Ally/Enemy retains rolled order. Patron/Civilian randomly assigns the lower three within STR/DEX/END and the upper three within INT/EDU/SOC; Combatant reverses those groups. Aslan applies STR +2 and DEX -2; Vargr applies STR -2, DEX +1 and END -1. Levels 2, 4, 6 and 8 each add one to a random attribute; levels 9-12 each remove one from a random attribute. Attributes are clamped to 3-12 after racial modifiers and each level adjustment; an adjustment at a boundary remains at that limit. UPP is encoded as six uppercase hexadecimal digits (A/B/C for 10/11/12) and remains editable. In unsaved drafts, changing race, type or skill level regenerates UPP; changing profession preserves it. Existing saved NPCs are not automatically regenerated.

### NPC names and saved profiles

NPC generation selects a name from race- and gender-specific pools: Human given/family names, Aslan given/clan names, and Vargr given/pack names. These are original flavour names. In a new draft, selecting Human, Aslan or Vargr regenerates the profile. Changing gender refreshes the automatic name only while Name still matches the previous suggestion; a referee-entered name is preserved when gender changes. The Name field stays editable for saved NPCs. Saved NPC Type, Occupation, Race and Skill Level controls are read-only, and their regeneration handlers also reject saved profiles. Other editable fields and the Skills/Equip panels remain available.

### Race selection and manual profiles

Race is a dropdown containing Human, Aslan, Vargr, Droyne, Bwap, K'Kree, Hiver, Dolphin, Gorilla and Robot. Only Human, Aslan and Vargr support automatic generation. Selecting another race clears only Name, Gender, Age and UPP for manual entry. Occupation, generated skills, quirks, token, NPC Type and Skill Level are preserved. Changing type or profession can reroll skills, and changing skill level rerolls skills without populating manual age or UPP. Empty UPP is preserved on Save for manual races. Selecting Human, Aslan or Vargr again generates name, gender, age, UPP and skills for the current type and level. Saved NPC Race remains read-only.

### NPC quirks

Each newly generated NPC rolls D66 twice on the supplied 36-entry Character Quirks table. Matching results retain the first quirk and leave Quirks 2 blank; duplicates are not rerolled. The two quirk fields remain editable and persist with the NPC. Race, profession and skill-level changes retain existing quirks, as do edits of saved NPCs.

### Combatant loadouts and editor layout

New Combatants receive a proposed Supply Catalog loadout: usable armour, a ranged infantry weapon and a melee backup where available. Selection favours conventional cloth/flak/ballistic armour, respects explicit armour skill requirements, excludes battle dress, and prefers standard rifles/carbine/pistol patterns suited to the NPC's Gun Combat speciality. Heavy launchers/artillery and natural weapons are excluded from the standard loadout. Armour tech-level variants prefer the lower TL within the same preferred class. Choices are shown before Save, are refreshed when draft skills change, and are persisted atomically at quantity 1 with Worn/Equipped enabled. Catalogue entries are reused rather than copied. Missing categories are skipped; an empty/incompatible catalogue leaves no proposed loadout. Existing saved NPC equipment is never reset by profile editing and remains editable through Equip.

The editor uses three desktop rows: Name / NPC Type / Skill Level / Occupation / Race; Gender / UPP / Age; and Quirks 1 / Quirks 2 in equal halves. Narrow screens wrap the identity fields into two columns and stack fields on small phones. Skills, equipment preview and token controls follow below.

## Scenes and Battlemap

The docked Combat Tracker stores the encounter roster for each scene, including combatants that have not been placed. Active Travellers appear automatically, once each, before NPCs; inactive Travellers are excluded and are reconciled when returning to the Battlemap. Search Add NPC by name, occupation or race, then select a result to add an instance. Repeated selections create independently numbered NPC instances. Instance names are editable without changing the source NPC. The roster scrolls independently of the map to keep larger encounters compact.

Each row has a visibility checkbox and a pin button for placing/repositioning the token: click the pin, then click a grid square. The minus button unplaces a token while retaining its tracker entry; × removes an NPC instance from the encounter. Each placed token occupies one grid square and moves/resizes with the grid and zoom. Uploaded character images retain their aspect ratio; missing/unusable images show initials. Drag tokens to snap between squares and drag the background to pan. Instance identities, names, visibility and optional grid positions persist in the database. The CombatTracker migration preserves existing placements and converts each existing NPC token into instance 1. Deleting a scene or character cascades its instances.

The toolbar uses the same colour picker as the Scenes editor and changes grid colour, line width and opacity immediately and saves them without replacing the image or resetting pan/zoom. The Cast glyph opens a read-only Battlemap presentation paired to this Admin tab in the same browser profile/origin. It follows camera, token and grid updates. Unchecked combatants appear greyed out to the GM and are excluded from the player snapshot; unplaced instances are excluded too. The presentation has no editing or panning controls. Navigating away retains the last presented view; returning resumes updates. Close clears the player map. Presentation snapshots use a separate BroadcastChannel and storage key from the Home sector map.

Scenes are campaign-specific battlemap definitions with a background image stored in the database (PNG, JPEG, GIF or WebP, maximum 4096 × 4096 pixels), name, grid size (default 100 image pixels), colour (black), opacity (50%) and line width (2 screen pixels). Each square represents 1.5 m × 1.5 m. Add/Edit use an inline editor; editing settings without uploading a new image keeps the existing background. Delete confirms removal of the scene and its image. Deleting a campaign cascades its scenes. The Scenes migration runs at startup and retains existing campaign data.

Scenes appears in navigation immediately above Battlemap. Battlemap is disabled until a scene is opened. Opening replaces the currently open scene and starts fit-to-page. The Battlemap uses PixiJS with separate background, token, fog and screen-space grid layers. Large images use an overview and visible high-resolution tiles. Grid strokes retain their configured screen-pixel width at every zoom. The Battlemap shows the image with its configured square grid; drag to pan, use +/− or the mouse wheel to zoom, and Fit to page to reset. Zoom anchors to the mouse position when using the wheel. Pan and zoom survive navigation to other views and back, using per-open-scene browser session storage. Close clears the open scene, disables its navigation link and returns to Scenes. Changing campaigns closes the current map. Open-scene state is scoped to the current browser circuit; refreshing the application starts with no scene open.

Large images are fetched directly through the campaign-scoped image endpoint rather than sent through UI state. Scene lists query metadata without loading image bytes. Uploaded images remain local to this application's database. Image or grid edits in the Scenes editor advance the scene revision and reset the open viewport when next displayed; live toolbar grid edits preserve the revision and camera. Controls remain available for changing the scene through Scenes; closing does not delete it. Narrow screens adapt the editor and toolbar layouts.

Checks: `node MTUAssistant/Components/Map/Battlemap.test.mjs` covers fit, anchored zoom, bounds and saved view restoration; `BattlemapPresentationSync.test.mjs` checks public token filtering, late joining, read-only behaviour and session isolation. `MTU.RuntimeChecks/SceneChecks.cs` covers preserving legacy placements during migration, active Traveller synchronization, repeated NPC instances, independent edits/visibility/placement, live grid settings, campaign isolation, dimension limits and cascading deletes.



New and replacement scene images are limited to 4096 pixels on each axis rather than a file-size limit. PNG, JPEG, GIF and WebP canvas dimensions are checked at upload and again in the storage service without decoding full pixel buffers. Upload feedback includes the selected dimensions. Existing stored images are retained without conversion. The limit is defined once in SceneImageInfo.MaxDimension; no graphics backend change is made. SceneImageChecks covers supported headers, malformed metadata, width/height boundaries and 4096 × 4096 acceptance. SceneChecks also verifies saving a valid image larger than the former 20 MB cap.
